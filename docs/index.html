Ein agentisches Multi-Agent-System für didaktische Code Reviews

CodeMentor analysiert GitHub Pull Requests zusammen mit ihren CI-Ergebnissen und erzeugt daraus lernorientiertes Feedback. Es erklärt statt zu patchen, prüft das Verständnis mit Mini-Testaten und passt jedes weitere Review an das an, was der Studierende bereits verstanden hat.

Demo ansehen Repository Selbst ausprobieren
Das Problem

Code Review sagt, was falsch ist. Nicht warum.

Ein Studierender öffnet einen Pull Request. Die CI wird rot. Was er bekommt, ist das hier: 

tests/test_rechner.py::test_divide_by_zero FAILED
E   ZeroDivisionError: division by zero

rechner.py:14: error: Item "None" of "int | None" has
    no attribute "__len__"  [union-attr]

Technisch korrekt. Didaktisch wertlos. Und der bequemste Ausweg — der „Apply fix"-Knopf eines KI-Assistenten — ist zugleich der lernfeindlichste: der Fehler verschwindet aus dem Code, aber nicht aus dem Kopf.

CI-Tools

Liefern Findings, keine Erklärungen. Für Anfänger oft unlesbar.

KI-Assistenten

Liefern fertige Fixes. Man übernimmt sie, ohne sie zu verstehen.

Beide

Vergessen alles. Beim nächsten PR fängt derselbe Fehler von vorne an.

Die Einsicht

Alle Werkzeuge optimieren den Code. Keins den Entwickler.

Bestehende Tools sind auf den Zustand des Artefakts optimiert. Lernen ist aber ein Prozess über viele Reviews hinweg, kein Ereignis in einem einzelnen. Daraus folgt die zentrale Anforderung: das System braucht ein Gedächtnis.

Genau das unterscheidet CodeMentor von „ein LLM über den Diff laufen lassen". Ein einzelner Prompt hat keinen Begriff davon, was dieser Mensch letzte Woche schon verstanden hat.

Der Lernkreislauf

1 · Analysieren

Pull Request, CI-Findings und Review-Kommentare werden gemeinsam ausgewertet.

2 · Erklären

Feedback mit Begründung, Doku-Zitat und sokratischer Rückfrage — statt fertiger Lösung.

3 · Nachfragen

Der Studierende antwortet im Chat. Das System erkennt, ob das Konzept verstanden wurde.

4 · Prüfen

Ein Mini-Testat verifiziert das Verständnis und wird bewertet.

5 · Anpassen

Das Lernprofil wird aktualisiert — das nächste Review fällt anders aus.

↻ Und von vorn

Review Nr. 4 sieht anders aus als Review Nr. 1. Das ist der Punkt.

Architektur

Vier Agenten, ein Graph

Orchestriert über LangGraph. Der Reflection Agent entscheidet bei jedem Review neu, welcher Agent als nächstes läuft — nicht jeder Pull Request durchläuft alle Stationen.

Reflection Agent

Wertet PR, CI-Findings und Kommentare aus und entscheidet über den weiteren Weg — inklusive der Entscheidung, gar nichts zu tun.

Dev-Mentor Agent

Erzeugt Erklärungen, Lernziele, sokratische Fragen und belegt sie mit Zitaten aus echter Dokumentation.

Learning Agent

Extrahiert Konzepte und Schwierigkeitsgrad und entscheidet, wann ein Mini-Testat fällig ist.

Praise Agent

Erzeugt begründetes positives Feedback, wenn es nichts zu bemängeln gibt — statt eines leeren Reviews.

Was „agentisch" hier konkret heißt

Nicht jede Entscheidung gehört ins Sprachmodell. Faktenfragen werden deterministisch im Code beantwortet, Urteilsfragen vom LLM. Dadurch bleibt das Routing reproduzierbar, unabhängig von Modellgröße und Tagesform.

Deterministisch im CodePer LLM
Liegt belastbare Evidenz vor?Welches Konzept fehlt hier?
Ist die Änderung trivial?Wie erkläre ich es didaktisch?
Ist die Doku-Quelle relevant genug?Welche Frage führt zur Einsicht?

Das System beschafft sich seine eigene Evidenz

In Demo-PR #5 wird eine Hilfsfunktion entfernt. Der Diff allein reicht nicht, um daraus konkretes Feedback abzuleiten — also durchsucht das System eigenständig das Repository nach verbliebenen Aufrufern, findet einen, und erklärt dem Studierenden den Zusammenhang, den der Diff nicht zeigt. Fehlt Dokumentation zu einem Thema, wird sie on-demand nachindexiert.

Umsetzung

Technische Entscheidungen

Kalibrierte RAG-Schwelle

Empirisch gemessen: relevante Treffer lagen bei L2-Distanz 0,17–0,25, irrelevante bei 0,36–0,43. Schwelle auf 0,32. Lieber ehrlich „keine passende Doku" als eine schwache Quelle zitieren.

Modellwahl nach Schema-Treue

Wechsel auf devstral-2-123b, weil die zuverlässige Einhaltung des JSON-Schemas der Engpass war — nicht die Sprachqualität.

Fehler statt Stille

Drei Retries bei transienten API-Fehlern, danach eine verständliche Meldung in der UI — statt eines leeren Reviews, das nach einem Ergebnis aussieht.

Ausprobieren

In vier Befehlen lokal starten

Warum es hier keine öffentliche Instanz gibt CodeMentor braucht ein Python-Backend und einen persönlichen AcademicCloud-API-Key. Eine öffentlich erreichbare Demo würde auf einem einzelnen fremden Schlüssel laufen — das ist weder tragfähig noch sinnvoll. Der Screencast oben zeigt den vollständigen Ablauf; lokal ist das Projekt in wenigen Minuten lauffähig. 
git clone https://github.com/Ishak-Erol/AAI_CodeMentor.git
cd AAI_CodeMentor
pip install -e ".[dev]"
cp .env.example .env      # API_KEY und GITHUB_TOKEN eintragen
uvicorn server:app --reload

Dann http://127.0.0.1:8000/threads öffnen. Die Datenbank wird automatisch angelegt. Vollständige Anleitung inklusive PowerShell-Variante im README.

Einen Demo-PR direkt über die Kommandozeile analysieren:

python main.py --owner Ishak-Erol --repo codementor-demo-target --pr 1 --rag
Ehrlichkeit

Was CodeMentor heute nicht kann

  • Kein öffentliches Deployment — die Anwendung benötigt einen eigenen API-Key.
  • Auf Python zugeschnitten — die CI-Parser verstehen Ruff, mypy und pytest. Andere Sprachen bräuchten eigene Parser.
  • Didaktische Wirksamkeit nicht evaluiert — das Konzept ist umgesetzt, aber nicht mit echten Studierenden gemessen.
  • Offene Typfehler im eigenen Code — mypy meldet noch Findings; Ruff läuft vollständig grün.

Wohin es gehen könnte

  • Weitere Sprachen über austauschbare CI-Parser
  • Dozenten-Sicht auf den Lernstand einer ganzen Kohorte
  • Evaluation mit echten Studierenden über ein Semester
